## Procedimiento manual para levantar pruebas locales

1. Revisar rama/diff/manifest. Requiere Supabase CLI compatible con este TOML, Docker funcionando y puertos libres. No ejecutar `supabase link`, `db push`, `--linked`, `--db-url`, `migration repair`, ni comandos remotos. No cargar `.env` de otro worktree. Si se necesita staging remoto, requiere autorización separada para crear/configurar/aplicar/desplegar allí: este paquete no lo ejecuta.
2. Generar copias: `node scripts/prepare-checkout-staging.mjs`. Verificar hashes y versiones únicas contra manifest. Solo se permite el baseline en un proyecto completamente nuevo. No copiar `tests/fixtures/storage-permissions.sql` a Supabase: el stack ya crea Storage real; esa fixture solo se usa en PostgreSQL efímero.
3. Configurar un widget **Turnstile de staging** y dominios locales de prueba autorizados. Ingresar secret en `SUPABASE_AUTH_CAPTCHA_SECRET` de la terminal de Supabase, sin guardarlo en archivos versionados ni compartirlo en informes. Configurar site key público en la app. La clave/secreto deben corresponder al mismo widget. Para pruebas locales sin widget real, los test keys oficiales del proveedor no prueban protección real y deben identificarse como prueba, nunca producción. No desactivar CAPTCHA ni habilitar invitado si el proveedor no valida efectivamente.
4. Desde raíz, ejecutar `supabase start --workdir staging`. **Aplica automáticamente migrations y seed locales**, inicia contenedores y consume espacio/red. Es una acción manual local explícita; aquí no se ejecutó. Si el CLI exige completar campos, generar defaults con `supabase init` en un directorio temporal nuevo, revisar la diferencia y conservar IDs/puertos/seed/Auth/CAPTCHA de este archivo; no sobrescribirlo ni adoptar defaults sin CAPTCHA. `supabase status --workdir staging` debe mostrar solo URLs loopback. No mostrar keys en un reporte.
5. Crear un archivo `.env.local` **solo en este worktree** usando `staging/app.env.example`. Copiar únicamente URL/anon/service keys del proyecto **local**; nunca credenciales productivas. Definir ADMIN_ALLOWED_EMAILS para un usuario de prueba propio. La identidad administrativa no puede ser anónima. Crear ese usuario de contraseña en Auth Studio local y confirmarlo si hace falta; no usar cuentas reales ni correo remoto. `CHECKOUT_GUEST_ENABLED=true` solo en este runtime, con site key válido. La lista heredada del proyecto y configuración pendiente comercial siguen intactas.
6. Ejecutar `npm run build` y `npx tsc --noEmit`; iniciar app `npm run start -- --hostname 127.0.0.1 --port 3107`. Abrir `http://localhost:3107`. Cookie Secure con build de producción necesita un navegador que trate loopback como origen confiable; si no la conserva, resolver HTTPS local antes de continuar, no quitar flags. No desplegar para sortear el problema.
7. Ejecutar los escenarios debajo con dos perfiles limpios de navegador (compradores A/B) y uno administrativo. Inspeccionar Auth: A debe ser `is_anonymous=true` y getUser debe verificar su identidad; SQL role es authenticated, no anon sin sesión. Revisar CAPTCHA válido, inválido y expirado en perfiles nuevos sin cookie (una sesión ya verificada se reutiliza sin crear otra identidad); sesión persistida y recuperación de cookies. Prueba real del proveedor pendiente, no sustituida por mocks.
8. Cerrar app y `supabase stop --workdir staging` cuando termine. No activar cron. Un reset o borrado de volumen es destructivo local: revisar identidad/proyecto y nunca dirigirlo a otra base. Para repetir desde vacío, usar un proyecto local nuevo o reset local de este único stack tras revisar su ID y ruta.

## Escenarios funcionales de aceptación

1. Invitado A: carrito del producto sintético, transferencia/retiro, nombre/teléfono sin email. Cantidad 2: lista 200, descuento 50, total 150, stock 30→28, reserva 24h, pago pendiente. Doble clic/reintento reutiliza UUID y no duplica. Cambiar catálogo después no altera pedido creado. No enviar precio/total del cliente como fuente autorizada.
2. B: acceso al recibo/GET cotización de A debe negar (404 genérico/sin datos). Sin sesión también debe negar. SQL anon/authenticated no pueden escribir orders/stock ni ejecutar RPC de acreditación/expiración. Invitado incluso con email allowlisted no es admin. Cookie corrupta/perdida con operación pendiente no crea otra identidad silenciosamente.
3. Admin local: `/admin/checkout`, ingresar importe exacto y reconocimiento de recepción **simulada**, referencia sintética. Una sola evidencia de pago; repetición idempotente; pedido confirmado y pago paid son campos distintos. Invitado no accede a esa acción.
4. Efectivo/retiro: crear otro pedido pendiente. Antes de 24h no libera. Para no esperar, **solo en SQL Editor de Studio local sintético**, avanzar el fixture: `update public.checkout_operations set expires_at=clock_timestamp()-interval '1 second' where order_id='<UUID DEL PEDIDO SINTÉTICO>';`. Luego pulsar liberación manual autorizada en admin dos veces: libera exactamente una vez. Una reserva bloqueada se omite con SKIP LOCKED; repetir manualmente cuando termine la operación que retiene el lock. No asumir que un solo lote garantiza liberar todas las filas vencidas. Aplicar ese cambio de timestamp a un pedido ya pagado y comprobar que nunca devuelve stock. No ejecutar esto en una base remota ni sobre registros reales.
5. Envío a Córdoba/Synthetic City/5000: cantidad 2, total 162.50 (=150+12.50), descuento no afecta envío. Cambiar destino invalida selección. Tarifa/revisión modificada rechaza quoteKey viejo para pedidos nuevos; reintento de pedido existente conserva total.
6. Destino Jujuy/localidad sintética/4600/dirección: sin tarifa, solicitar cotización; no crea pedido, importe ni reserva. Repetición genera la misma solicitud. Admin ve contacto/productos; comprador solo estado propio. No hay contratación de transporte ni conversión automática de cotización.
7. Mercado Pago no aparece. GET y POST `/api/mercadopago/create-preference` y `/api/mercadopago/webhook` deben devolver 410/AUTOMATIC_PAYMENTS_DISABLED, sin llamadas al SDK. No configurar keys, webhooks ni conciliación MP.

El build no sustituye esa prueba.

Si no hay ledger, no inferir aplicación. Objetos actuales pueden provenir de overrides posteriores; no permiten deducir qué 002 fue registrado. No borrar/renombrar/repair archivos aplicados ni decidir un mapping sin esa evidencia. La resolución de este paquete nuevo no es un repair autorizado de Production.
